# Результати перевірки ПР11

## Локальний прогін mock із кешем і без нього

Один і той самий потік із 12 замовлень (`seed=1`) прогнано з `LLM_PROVIDER=mock`, спершу з `CACHE_ENABLED=0`, потім з `CACHE_ENABLED=1`. Для вимірювання швидкості встановлено `MOCK_FIRST_DELAY_MS=20`, `MOCK_DELAY_MS=10`; частоту запитів збільшено до 100/хв.

| Показник | Без кешу | З кешем |
|---|---:|---:|
| Завершені замовлення | 12 | 12 |
| Влучання в кеш | 0 | 5 |
| Звертання до провайдера | 12 | 7 |
| Вхідні токени | 3192 | 1860 |
| Вихідні токени | 1464 | 846 |
| Розрахована вартість | $0.004618 | $0.002673 |
| Медіана wall time | 0.18 с | 0.13 с |
| p95 wall time | 0.22 с | 0.22 с |

У цьому тестовому потоці кеш скоротив виклики, токени й вартість приблизно на 42%; медіана часу зменшилася приблизно на 28%, але p95 не змінився. Замовлення з кешу мають фактичні нульові витрати й не списують бюджет. Часові числа характерні лише для локального mock і 50-мс інтервалу опитування `eval/replay.py`, а не для навантаження реального провайдера.

## Інші перевірки

- `python check_env.py` — успішно; локальний mock не потребує `.env` чи API-ключа.
- `python -m compileall -q app eval check_env.py` — успішно.
- Інтеграційно перевірено створення чернетки, usage і вартість mock, кеш-хіт без додаткового списання, `fresh`, повтори mock-збою, fallback на mock без ключа, rate limit `429`, validation `422` та request ID в заголовку й тілі помилки. Вичерпаний бюджет дає `202` для фонового завдання, а потім контрольовану помилку `budget` (`retryable: false`) із часом відновлення; кеш-хіт після вичерпання обслуговується, а промах відхиляється до виклику провайдера.
- `eval/analyze.py` обробив журнал тестового прогону; сценарій перевірки підтвердив наявність звітів про повільні/невдалі/повторні виклики, витрати й кеш.
- Перевірено тестовий журнал на відсутність імені клієнта, номера замовлення та значення API-ключа.
- Перевірено, що скасування під час backoff перериває очікування повтору й шлюз повертає `ProviderError(kind="cancelled")`.

Реальний Gemini/OpenAI-сумісний endpoint не викликався, тому його фактичний `usage`, тарифікація та сумісність `stream_options` потребують окремої перевірки з власними обліковими даними.
